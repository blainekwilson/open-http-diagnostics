# Level 2 — Trace Context Establishment and Propagation

**Status:** Draft 0.4  
**Level:** 2

## 1. Purpose

Level 2 ensures that a participating HTTP layer has usable W3C Trace Context and a matching `OHD-Trace-ID` for downstream propagation and logging.

Header definitions are authoritative in [OHD HTTP Header Fields](header-fields.md).

## 2. Processing model

A Level 2 participant performs the following steps:

1. Read the incoming `traceparent`, `tracestate`, and `OHD-Trace-ID` fields.
2. Process `traceparent` according to W3C Trace Context.
3. If no usable Trace Context exists, establish a new trace using a cryptographically suitable identifier source.
4. Create the outgoing parent ID required for the next hop.
5. Derive `OHD-Trace-ID` from the effective trace ID.
6. Forward `traceparent`, applicable `tracestate`, and `OHD-Trace-ID` downstream.
7. Record the effective trace information and its source.

## 3. Identity and spans

The trace ID identifies the end-to-end trace. A participant may create a new parent ID for an outgoing request. Therefore the complete `traceparent` value is not expected to remain identical across every hop.

`OHD-Trace-ID` remains stable because it contains only the trace ID.

## 4. Incoming combinations

### 4.1 Usable `traceparent`; matching or absent `OHD-Trace-ID`

Continue the trace and set outgoing `OHD-Trace-ID` to the effective trace ID.

### 4.2 Usable `traceparent`; conflicting `OHD-Trace-ID`

Treat `traceparent` as authoritative. Replace the outgoing `OHD-Trace-ID` with the effective trace ID. Record a mismatch event when supported.

### 4.3 Missing or unusable `traceparent`; any `OHD-Trace-ID`

Establish a new trace. Do not construct a new `traceparent` from the received OHD convenience field. Replace outgoing `OHD-Trace-ID` with the newly generated trace ID.

### 4.4 `tracestate`

Process and forward `tracestate` only as permitted by W3C Trace Context. An orphaned `tracestate` without usable `traceparent` must not be treated as authoritative trace state.

## 5. Recommended diagnostic fields

Level 2 implementations should expose:

| Field | Meaning |
|---|---|
| `trace_id` | Effective 32-character trace ID |
| `parent_id` | Parent ID observed or generated by this layer |
| `trace_flags` | Effective W3C trace flags |
| `trace_source` | `incoming`, `generated`, or `restarted` |
| `ohd_trace_id_mismatch` | Boolean indicating a conflicting incoming convenience field |

These are structured diagnostic fields and do not change Level 1 positional ordering.

## 6. Trust boundary

Trace fields received from clients are untrusted. Implementations must not use them for authentication, authorization, security policy, tenant selection, or privileged routing.

## 7. Failure behavior

Trace processing should fail open for application availability unless an operator explicitly configures stricter behavior. A tracing error should not normally prevent an otherwise valid HTTP request from being processed.
